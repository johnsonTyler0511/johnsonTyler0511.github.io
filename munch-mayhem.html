Project · Game Development · Agentic Engineering

Munch Mayhem In progress — playable prototype

An idle/tycoon game in Godot 4, built as a deliberate case study in agentic software engineering: how far an AI-assisted workflow can carry a project from an empty editor to a shipped game.

The game is still in development. What exists today is a playable prototype: three upgradeable stations, staff hiring, a gear system, customers and servers, and a procedurally generated kitchen on every launch. This page covers the working method and the tech underneath it.

Godot 4 · GDScript · Voronoi Procgen · A* Pathfinding · Claude Code

01 / Overview

Overview

Munch Mayhem is an Eatventure-style idle game. Stations cook on a timer and pay out, upgrades raise the payout and shorten the cycle, sous chefs double a station's speed, and a gear crate stacks a global earnings multiplier. Customers walk in the front door, order at the register, sit at a table, and pay when a hired server delivers their plate. No server, and they leave hungry.

The project has three goals, in priority order: test how far pure "vibe coding" can go, test whether a vibe-coded game can be cleaned up and released, and build Godot fluency. The standing rule is that ships faster, teaches more beats more impressive but won't get finished. Target: a playable, released game by the end of 2026.

02 / Workflow

Agentic Development Cycle

The game is pair-engineered with an AI coding agent (Claude Code). I write the design notes, set the phases, and make the calls; the agent writes the GDScript, keeps the documentation current, and runs the verification. A few rules keep that loop honest.

Plans and code live in different places. Design notes, roadmaps, and decisions live in a notes vault; the repo holds only code and a docs/ folder that describes what is actually built. The agent reads docs/ before touching anything and updates it in the same change, so the docs never drift from the code.

Every change gets a machine-checkable smoke test. A headless Godot run plays 3,000 frames and must exit clean: scripts parse, the main scene boots, the first station earns money, and a save file lands on disk. It takes about ten seconds and runs after every edit, which catches the class of bug the editor would only reveal on the next manual launch.

The first MVP was a one-shot. Rather than a phased fundamentals prototype, the first build went from empty editor to three stations, a gear crate, and JSON save/load in a single session. The phased plan stayed in the vault as a reference and the MVP became the test rig for everything since.

Playtests answer fixed questions. Each build ships with a written list of what to evaluate, and the findings go back into the plan before the next phase starts. The procedural generation work below was selected exactly this way, by playing candidates side by side on the same seed.

Why this counts as engineering

The interesting question is not whether the agent can write GDScript, but whether the surrounding process produces a codebase a person can still reason about. The architecture that fell out is deliberately small: one state singleton, pure-function economy tuning, signal-driven UI that re-reads state instead of caching it, and UI built in code so the code is the spec. Those choices were made to keep the whole game readable in one pass, by a human or an agent.

03 / Procgen

Voronoi Floor-Plan Generation

Every launch generates a new 28×28-tile kitchen. The generator started as a standalone sandbox project built around the Strategy pattern: a LevelGenerator base class with one shared tile vocabulary, and a dropdown to swap the algorithm behind it. Thirteen strategies were built and compared on the same seeds: binary space partitioning, cellular automata with three different "boxify" post-processes, a BSP+CA hybrid, and a family of Voronoi variants differing in distance metric (Euclidean, Manhattan, Chebyshev) and seeding (random, jittered grid, Poisson disk, role-based).

The winner was Voronoi with role-based seeds on a jittered grid. BSP produced rooms that were tidy but samey; cellular automata produced organic caves that never read as a restaurant. Voronoi cells gave irregular, believable rooms, and assigning roles to specific seeds (kitchen in a corner, host stand in the opposite corner, register near the front) gave every layout a sensible flow from door to table to kitchen.

The pipeline places seeds, tags each tile with its nearest seed, and optionally runs Lloyd relaxation, nudging each seed toward its cell's centroid so cell sizes even out. The role-based variant switches relaxation off, because moving the seeds would undo the deliberate corner placement; the jittered grid supplies the even spacing instead. Cells under ten tiles are folded into their largest neighbour, one-tile walls go up along every cell boundary, a centred doorway is punched through each shared edge (two tiles wide between kitchen and dining), and a front entrance opens in the cell with the most outer-wall tiles.

Equipment placement guarantees one of each station type, then scatters tables, barrels, a register, and a host stand. Generation retries if a layout has no entrance, no register, or fewer than three reachable tables. The result feeds an AStarGrid2D over the walkable tiles, which is what the chef, servers, and customers all path on.

04 / Systems

Game Systems

The runtime is four Godot autoloads with one responsibility each, load-ordered by dependency:

  • Economy — pure functions only. Cost curves, cycle times, payouts, and number formatting with K / M / B / T suffixes so late-game balances stay readable. All balance tuning lives in this one file.
  • GameState — the single source of truth for money, stations, gear, servers, and customers served. Mutator methods (try_upgrade_station, try_hire_server, try_open_crate, …) change state and emit signals; nothing else owns mutable game state.
  • SaveManager — listens to those signals, debounces half a second, and writes JSON to user://save.json. Also flushes on window close. The schema is versioned, with migrations from v1 to v2 already exercised when servers were added.
  • Location — runs the generator at boot, builds the A* grid, and derives the front-of-house layout: entrance, register, order spot, server home, and table/seat pairs.

Station progress is ticked centrally in GameState rather than in per-widget timers, so save data is always the source of truth and a reload resumes mid-cycle with no per-widget restore logic. The UI never caches derived state; every widget re-reads on every signal, which is wasteful in CPU terms and correct by construction.

The front-of-house simulation is the one exception to "everything lives in GameState." Customers and servers are transient agents with two small state machines (ENTER → ORDER → SEAT → WAIT → EAT → LEAVE and IDLE → TO_KITCHEN → PICKUP → TO_TABLE → DELIVER → RETURN), positioned in tile space and converted to pixels only at draw time. They write back to the persistent state through a single complete_order() call. Customers who wait longer than their patience turn angry, pay nothing, and leave; that pressure is the entire incentive to hire servers.

All art is procedural. One CharacterSprite class draws chefs, sous chefs, servers, and customers as chibi figures from vector primitives, varying hat, outfit, hair, and skin per role. Tiles and furniture are drawn the same way. Keeping everything behind a single _draw() means swapping in real sprite art later is a mechanical change, which is the plan if the game gets to release.

05 / Status

Where It Stands

In progress. The prototype is playable end to end: buy and upgrade stations, hire staff, open crates, serve customers, and come back to a saved game. It is not yet a released game.

Done so far: the one-shot MVP (stations, gear, save/load), the procgen sandbox and its playtest, porting the winning generator into the game with A* movement, the customer and server layer, and the code-drawn character and tile art pass.

Next up, roughly in order: sound and particles (the "juice" pass), a mobile-portrait layout, offline earnings, more stations, and locations with prestige, which is where the procgen work pays off, since each new location becomes a fresh generated kitchen. Beyond that, the release test: cleaning up a vibe-coded game far enough to ship it.
